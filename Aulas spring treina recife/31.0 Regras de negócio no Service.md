## 💠 O que é uma regra de negócio?

Regra de negócio é uma restrição que não vem do banco de dados nem da validação de formato — vem da **lógica do domínio**. Exemplos:

- Um usuário não pode ser deletado se for responsável por projetos ativos
- Um projeto não pode ser deletado se tiver tarefas vinculadas
- Um agendamento não pode ser criado para uma data já ocupada

Essas regras vivem no **Service** — que é a camada responsável pela lógica da aplicação.

---

## 💠 Regra 1: não deletar usuário com projetos vinculados

```Java
public void deletarUsuarioPorId(Long id){

    Usuario usuario = usuarioRepository.findById(id).orElseThrow(
        () -> new ElementoNaoEncontradoException("Não foi encontrado Usuario com o Id solicitado.")
    );

    if (projetoRepository.existsByResponsavel_Id(id)) {
        throw new RegraDeNegocioVioladaException(
            "O usuário não pôde ser deletado pois existem projetos em que ele é o responsável."
        );
    }

    usuarioRepository.delete(usuario);
}
```

O fluxo:
1. Busca o usuário — se não existir, `404`
2. Verifica se existe projeto com esse usuário como responsável
3. Se sim, `422` com mensagem descritiva
4. Se não, deleta

## 💠 Regra 2: não deletar projeto com tarefas vinculadas

```Java
public void deletarProjetoPorId(Long id){

    Projeto projeto = projetoRepository.findById(id).orElseThrow(
        () -> new ElementoNaoEncontradoException("Não foi encontrado Projeto com o Id solicitado.")
    );

    if (tarefaRepository.existsByProjeto_Id(id)) {
        throw new RegraDeNegocioVioladaException(
            "O Projeto não pôde ser deletado pois existem tarefas atreladas a ele."
        );
    }

    projetoRepository.delete(projeto);
}
```

## 💠 O método `existsBy` no Repository

Repara que não usamos `findBy` para buscar a lista e verificar se está vazia. Usamos `existsBy`, que retorna um `boolean`:

```Java
// Repository
boolean existsByResponsavel_Id(Long id);   // ProjetoRepository
boolean existsByProjeto_Id(Long id);        // TarefaRepository
```

A diferença é importante:

| Abordagem | O que faz | Custo |
|---|---|---|
| `findByResponsavel_Id(id).isEmpty()` | Carrega todos os objetos do banco pra memória só pra ver se a lista está vazia | Alto |
| `existsByResponsavel_Id(id)` | Executa `SELECT EXISTS(...)` no banco — só verifica se existe, sem carregar nada | Baixo |

O `existsBy` é sempre preferível quando você só precisa saber se existe, sem usar os dados.

---

## 💠 Por que `delete(usuario)` e não `deleteById(id)`?

No método de deletar, primeiro buscamos o objeto e depois chamamos `delete(objeto)` em vez de `deleteById(id)`. O motivo: o `deleteById` não lança exceção se o id não existir — ele simplesmente não faz nada. Buscando com `orElseThrow` antes, garantimos que o `404` seja lançado corretamente se o id for inválido.

---

> 💡 **Resumo:** regras de negócio ficam no Service. O método `existsBy` no repository verifica existência sem carregar dados — mais eficiente que buscar lista e verificar tamanho. A `RegraDeNegocioVioladaException` sinaliza que a lógica do domínio impediu a operação.
