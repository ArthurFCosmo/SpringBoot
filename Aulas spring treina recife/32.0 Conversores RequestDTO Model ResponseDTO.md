## 💠 O fluxo de conversão

Na versão 3.0, a entidade (`Model`) nunca chega ao Controller — e o RequestDTO nunca chega ao banco. Existe uma camada de conversão no Service que transforma os dados conforme necessário:

```
Controller
    │ recebe UsuarioRequestDTO
    ▼
Service
    │ converterRequestDTOParaModel() → Usuario (model)
    │ repository.save(model)         → Usuario (model salvo)
    │ converterModelParaResponseDTO() → UsuarioResponseDTO
    ▼
Controller
    │ devolve UsuarioResponseDTO
```

---

## 💠 `converterModelParaResponseDTO`

Transforma a entidade do banco no DTO de saída. É aqui que acontecem as transformações: mascaramento de CPF, cálculo de idade, formatação de dados:

```Java
private UsuarioResponseDTO converterModelParaResponseDTO(Usuario usuario){
    return new UsuarioResponseDTO(
        usuario.getId(),
        usuario.getNome(),
        mascararCPF(usuario.getCpf()),              // ← transforma
        usuario.getEmail(),
        usuario.getDataNascimento(),
        calcularIdade(usuario.getDataNascimento()), // ← calcula
        usuario.getStatus().toString()
    );
}
```

## 💠 `converterRequestDTOParaModel` — sobrecarga para create e update

O create não tem `id` (o banco gera). O update tem `id` (vem da URL). Para lidar com os dois casos, usamos **sobrecarga de método** — mesmo nome, parâmetros diferentes:

```Java
// Para criar — id = null, o banco gera automaticamente
private Usuario converterRequestDTOParaModel(UsuarioRequestDTO usuario){
    return new Usuario(
        null,           // ← id null = INSERT
        usuario.nome(),
        usuario.cpf(),
        usuario.email(),
        usuario.senha(),
        usuario.dataNascimento(),
        converterParaEnumStatus(usuario.status())
    );
}

// Para atualizar — id vem da URL
private Usuario converterRequestDTOParaModel(Long id, UsuarioRequestDTO usuario){
    return new Usuario(
        id,             // ← id preenchido = UPDATE
        usuario.nome(),
        usuario.cpf(),
        usuario.email(),
        usuario.senha(),
        usuario.dataNascimento(),
        converterParaEnumStatus(usuario.status())
    );
}
```

O `save()` do JPA decide automaticamente: se o objeto tem `id` preenchido e esse `id` existe no banco, faz `UPDATE`. Se o `id` é `null`, faz `INSERT`.

---

## 💠 Como o update usa o converter sobrecarregado

```Java
public UsuarioResponseDTO atualizarUsuario(Long id, UsuarioRequestDTO usuario) {

    usuarioRepository.findById(id).orElseThrow(
        () -> new ElementoNaoEncontradoException("Não foi encontrado Usuario com o Id solicitado.")
    );

    return converterModelParaResponseDTO(
        usuarioRepository.save(converterRequestDTOParaModel(id, usuario)) // ← passa o id
    );
}
```

O `id` vem do `@PathVariable` da URL, é validado com `orElseThrow`, e então passado para o converter — que monta o model com o `id` existente, fazendo o `save` entender que é uma atualização.

## 💠 O conversor de enum

O status chega como `String` no RequestDTO (`"ATIVO"`, `"INATIVO"`). Precisa virar o enum `StatusUsuario` para ser salvo. Isso também fica no service:

```Java
private StatusUsuario converterParaEnumStatus(String status){
    try {
        return StatusUsuario.valueOf(status.toUpperCase().strip());
    } catch (IllegalArgumentException e) {
        throw new RegraDeNegocioVioladaException(
            "Valor de STATUS inválido. Valores aceitos: ATIVO, INATIVO, BLOQUEADO."
        );
    }
}
```

- `.toUpperCase()` — aceita `"ativo"`, `"Ativo"` ou `"ATIVO"` sem diferença
- `.strip()` — remove espaços acidentais no início e fim
- O `catch` — se o valor não existir no enum, lança `422` com mensagem descritiva em vez de explodir com `500`

---

> 💡 **Resumo:** o Service tem três tipos de método de conversão — Model→ResponseDTO (para saída), RequestDTO→Model sem id (para create), RequestDTO→Model com id (para update). A sobrecarga de método permite o mesmo nome com parâmetros diferentes. O `save()` decide INSERT ou UPDATE pelo `id`.
