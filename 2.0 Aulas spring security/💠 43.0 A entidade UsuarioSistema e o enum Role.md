## 💠 Por que uma entidade separada para autenticação?

A SGP já tem um `Usuario` — a entidade que representa as pessoas cadastradas no sistema, com CPF, data de nascimento e status. Mas autenticação é uma responsabilidade diferente: precisa de email, senha hasheada e role de acesso.

Misturar as duas responsabilidades na mesma entidade seria como colocar o crachá de acesso dentro da ficha cadastral do funcionário — funciona, mas viola o princípio de separação de responsabilidades.

Por isso criamos `UsuarioSistema` — a entidade que o Spring Security vai usar exclusivamente para autenticação.

---

## 💠 O enum Role

Crie no pacote `enums`:

```Java
public enum Role {
    ADMIN,
    GERENTE,
    COLABORADOR
}
```

Define os três perfis de acesso da SGP:

| Role | Permissões |
|---|---|
| `ADMIN` | Acesso total — cria, lê, atualiza e deleta tudo |
| `GERENTE` | Lê tudo, cria e atualiza projetos e tarefas |
| `COLABORADOR` | Só leitura — não pode criar nem deletar |

## 💠 A entidade UsuarioSistema

Crie no pacote `model`:

```Java
@Data
@NoArgsConstructor
@AllArgsConstructor
@Entity
@Table(name = "TB_USUARIOS_SISTEMA")
public class UsuarioSistema implements UserDetails {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(nullable = false)
    private String senha;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private Role role;

    // Implementações do UserDetails

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
    }

    @Override
    public String getPassword() {
        return senha;
    }

    @Override
    public String getUsername() {
        return email;
    }

    @Override
    public boolean isAccountNonExpired() {
        return true;
    }

    @Override
    public boolean isAccountNonLocked() {
        return true;
    }

    @Override
    public boolean isCredentialsNonExpired() {
        return true;
    }

    @Override
    public boolean isEnabled() {
        return true;
    }
}
```

## 💠 O que é `UserDetails`

`UserDetails` é uma **interface do Spring Security** que define o contrato de um usuário autenticável. Ao implementá-la, você está dizendo ao Spring: "essa classe representa um usuário do sistema — você pode usar ela para autenticação".

O Spring Security não sabe nada sobre sua entidade `UsuarioSistema` por padrão. Mas quando ela implementa `UserDetails`, o Spring passa a entendê-la e a usar nos processos de autenticação e autorização.

Os métodos obrigatórios da interface:

| Método | O que retorna |
|---|---|
| `getUsername()` | O identificador único do usuário — usamos o email |
| `getPassword()` | A senha hasheada armazenada no banco |
| `getAuthorities()` | A lista de permissões/roles do usuário |
| `isAccountNonExpired()` | Se a conta não está expirada |
| `isAccountNonLocked()` | Se a conta não está bloqueada |
| `isCredentialsNonExpired()` | Se as credenciais não estão expiradas |
| `isEnabled()` | Se a conta está ativa |

Os quatro últimos retornam `true` por ora — não temos lógica de bloqueio ou expiração de conta nessa versão.

---

## 💠 O método `getAuthorities()`

```Java
@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
}
```

O Spring Security trabalha com **authorities** (permissões). Quando usamos roles, o padrão é prefixar com `ROLE_`:

- `Role.ADMIN` → authority `"ROLE_ADMIN"`
- `Role.GERENTE` → authority `"ROLE_GERENTE"`
- `Role.COLABORADOR` → authority `"ROLE_COLABORADOR"`

Esse prefixo é necessário para que o `@PreAuthorize("hasRole('ADMIN')")` funcione corretamente nas páginas seguintes.

## 💠 O UsuarioSistemaRepository

Crie no pacote `repository`:

```Java
@Repository
public interface UsuarioSistemaRepository extends JpaRepository<UsuarioSistema, Long> {
    Optional<UsuarioSistema> findByEmail(String email);
}
```

O `findByEmail` é o único método que precisamos — tanto no login (buscar o usuário pelas credenciais) quanto no filtro JWT (buscar o usuário pelo email dentro do token).

## 💠 O UserDetailsService

O Spring Security precisa de um componente que saiba como **carregar um usuário pelo username** (no nosso caso, o email). Esse contrato é a interface `UserDetailsService`:

```Java
@Service
@RequiredArgsConstructor
public class UsuarioSistemaService implements UserDetailsService {

    private final UsuarioSistemaRepository usuarioSistemaRepository;

    @Override
    public UserDetails loadUserByUsername(String email) throws UsernameNotFoundException {
        return usuarioSistemaRepository.findByEmail(email)
            .orElseThrow(() -> new UsernameNotFoundException(
                "Usuário não encontrado com o email: " + email
            ));
    }
}
```

O Spring Security chama `loadUserByUsername` automaticamente durante o processo de autenticação — quando o usuário faz login, ele usa esse método para buscar os dados no banco e comparar a senha.

---

> 💡 **Resumo:** `UsuarioSistema` é a entidade de autenticação — separada do `Usuario` do domínio. Ela implementa `UserDetails`, que é o contrato do Spring Security para usuários autenticáveis. O enum `Role` define os perfis de acesso com o prefixo `ROLE_` nas authorities. O `UsuarioSistemaService` implementa `UserDetailsService` para que o Spring saiba como buscar o usuário no banco pelo email.
