## 💠 O problema que o Spring Security resolve

A API SGP que construímos até agora tem um problema sério: qualquer pessoa que souber a URL consegue fazer qualquer coisa. Quer listar todos os usuários? `GET /usuario`. Quer deletar um projeto? `DELETE /projeto/1`. Não há nenhuma verificação de quem está fazendo a requisição.

Em produção, isso é inaceitável. Precisamos de duas coisas:

- **Autenticação** — "quem é você?" — o sistema precisa saber com quem está falando
- **Autorização** — "o que você pode fazer?" — nem todo mundo pode acessar tudo

O **Spring Security** é o módulo do ecossistema Spring responsável por resolver exatamente isso.

---

## 💠 Como o Spring Security funciona — a analogia do prédio

Pensa na sua API como um prédio corporativo.

Sem segurança, qualquer pessoa entra, sobe qualquer andar e acessa qualquer sala. Com o Spring Security, você coloca:

- Uma **portaria** na entrada — todo visitante precisa se identificar antes de entrar (autenticação)
- **Catracas por andar** — mesmo identificado, você só pode subir para os andares que seu crachá permite (autorização)
- Uma **recepção pública** — algumas salas são abertas para qualquer pessoa, como o saguão e o banheiro (endpoints públicos como login e registro)

O Spring Security implementa exatamente essa lógica na sua API.

## 💠 Onde o Spring Security atua na arquitetura

Na versão atual da SGP, o fluxo de uma requisição é:

```
Cliente
   │
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
```

Com o Spring Security, entra uma nova camada **antes** do Controller — o **Filter Chain** (cadeia de filtros):

```
Cliente
   │
   ▼
Filter Chain (Spring Security)
   │  ← verifica se a requisição tem credenciais válidas
   │  ← bloqueia ou permite a passagem
   ▼
Controller
   │
   ▼
Service
   │
   ▼
Repository
```

Se a requisição não tiver credenciais válidas, ela é barrada aqui — o Controller nem chega a ser chamado. O Spring Security age como um portão antes de tudo.

## 💠 O modelo que vamos usar — autenticação stateless com JWT

Existem várias formas de implementar autenticação. A mais comum em APIs REST modernas é a **autenticação stateless com JWT**:

- **Stateless** significa que o servidor **não guarda sessão**. Cada requisição carrega suas próprias credenciais — o servidor não precisa lembrar de ninguém entre uma chamada e outra.
- **JWT (JSON Web Token)** é o formato do "crachá" que o cliente carrega. É uma string compacta que contém informações do usuário (quem é, qual o seu perfil) e é assinada criptograficamente pelo servidor.

O fluxo completo fica assim:

```
1. Cliente faz POST /auth/login com email + senha
        │
        ▼
2. Servidor valida as credenciais no banco
        │
        ▼
3. Servidor gera um token JWT e devolve ao cliente
        │
        ▼
4. Cliente armazena o token (no Insomnia, num app, etc.)
        │
        ▼
5. Nas próximas requisições, o cliente envia o token no header:
   Authorization: Bearer <token>
        │
        ▼
6. O filtro JWT intercepta a requisição, valida o token
        │
        ▼
7. Se válido, a requisição chega ao Controller normalmente
   Se inválido ou ausente, retorna 401 Unauthorized
```

## 💠 Roles — controlando o que cada usuário pode fazer

Além de saber quem é o usuário, o sistema precisa saber o que ele pode fazer. Para isso usamos **roles** (perfis):

Na SGP, teremos três roles:

| Role | O que pode fazer |
|---|---|
| `ADMIN` | Acesso total — cria, lê, atualiza e deleta tudo |
| `GERENTE` | Lê tudo, cria e atualiza projetos e tarefas |
| `COLABORADOR` | Só lê projetos e tarefas — não pode criar nem deletar |

O role fica dentro do token JWT. Quando o filtro valida o token, ele também lê o role e o Spring Security verifica se aquele role tem permissão para acessar o endpoint solicitado.
