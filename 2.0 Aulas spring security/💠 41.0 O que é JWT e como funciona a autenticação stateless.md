## 💠 O problema da autenticação com sessão

Antes do JWT, o modelo mais comum de autenticação em aplicações web era baseado em **sessão**:

1. Usuário faz login → servidor cria uma sessão e guarda na memória
2. Servidor devolve um cookie com o ID dessa sessão
3. A cada requisição, o cliente manda o cookie → servidor busca a sessão na memória → valida

Isso funciona, mas tem um problema sério em APIs REST modernas: o servidor precisa **guardar estado**. Se você tiver dois servidores rodando ao mesmo tempo (o que é comum em produção), o usuário que fez login no servidor A não vai ser reconhecido pelo servidor B, porque a sessão está só na memória do A.

O JWT resolve isso eliminando o estado do servidor completamente.

---

## 💠 O que é JWT

**JWT** significa **JSON Web Token**. É um padrão aberto (RFC 7519) para transmitir informações de forma segura entre duas partes, usando uma string compacta e assinada digitalmente.

A ideia central é simples: em vez de o servidor guardar quem está autenticado, ele **escreve essa informação no próprio token** e devolve ao cliente. O cliente guarda o token e o envia em cada requisição. O servidor só precisa **verificar a assinatura** para saber que o token é legítimo.

É como um crachá corporativo com chip: você carrega ele, e o sistema da catraca só precisa ler o chip — não precisa consultar nenhum banco de dados de "quem está no prédio".

## 💠 A estrutura do token JWT

Um token JWT tem sempre três partes separadas por ponto (`.`):

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhcnRodXJAZ21haWwuY29tIiwicm9sZSI6IkFETUlOIiwiZXhwIjoxNzUzOTIwMDAwfQ.8Kf2mN9vXpQrTzLdYwJhCsUeBoAiMlRkVgNtDcHuEoY
```

Dividindo:

```
HEADER.PAYLOAD.SIGNATURE
```

### Header
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```
Define o algoritmo de assinatura usado (`HS256` — HMAC com SHA-256) e o tipo do token.

### Payload
```json
{
  "sub": "arthurcosmo@gmail.com",
  "role": "ADMIN",
  "exp": 1753920000
}
```
São os **claims** — as informações que o token carrega. `sub` é o subject (quem é o usuário), `role` é o perfil, e `exp` é o timestamp de expiração.

> ⚠️ O payload é apenas **codificado em Base64**, não criptografado. Qualquer um pode decodificar e ler. Nunca coloque senha ou dados sensíveis no payload.

### Signature
```
HMACSHA256(
  base64(header) + "." + base64(payload),
  segredo
)
```
É a assinatura digital. Gerada combinando o header + payload com a chave secreta que só o servidor conhece. Se alguém alterar qualquer coisa no payload, a assinatura deixa de bater — e o servidor rejeita o token.

## 💠 O fluxo completo na SGP

```
1. POST /auth/login
   body: { "email": "arthur@gmail.com", "senha": "1234" }
          │
          ▼
2. AuthService valida email + senha no banco
          │
          ▼
3. JwtService gera o token com email e role
          │
          ▼
4. Resposta: { "token": "eyJhbGci..." }
          │
          ▼
5. Cliente guarda o token

──────────────────────────────────────────

6. GET /projeto (requisição protegida)
   header: Authorization: Bearer eyJhbGci...
          │
          ▼
7. JwtAuthFilter intercepta — extrai e valida o token
          │
          ▼
8. Token válido → Spring Security autentica o usuário
          │
          ▼
9. Controller é chamado normalmente
          │
          ▼
10. Resposta com os projetos
```

## 💠 O que o token carrega na SGP

No nosso caso, o payload do token vai conter:

| Claim | Valor | Para que serve |
|---|---|---|
| `sub` | `arthurcosmo@gmail.com` | Identificar o usuário |
| `role` | `ADMIN` | Autorização por perfil |
| `iat` | timestamp de geração | Controle de validade |
| `exp` | timestamp de expiração | Rejeitar tokens velhos |

O `exp` é gerado automaticamente somando o tempo de expiração do `application.properties` ao momento atual. Depois de 24 horas (ou o tempo que você configurar), o token expira e o cliente precisa fazer login novamente.

## 💠 Por que stateless é melhor para APIs REST

|                    | Sessão (stateful)                      | JWT (stateless)                                     |
| ------------------ | -------------------------------------- | --------------------------------------------------- |
| Estado no servidor | ✅ Guarda sessão na memória             | ❌ Nada guardado                                     |
| Escalabilidade     | ❌ Difícil com múltiplos servidores     | ✅ Qualquer servidor valida                          |
| Performance        | ❌ Consulta de sessão a cada requisição | ✅ Só verifica a assinatura                          |
| Mobile/SPA         | ❌ Cookie nem sempre funciona           | ✅ Header Authorization funciona em qualquer cliente |

---

> 💡 **Resumo:** JWT é uma string com três partes — header, payload e signature. O payload carrega as informações do usuário (email, role, expiração). A signature garante que o token não foi adulterado. O servidor não guarda estado — só verifica a assinatura a cada requisição. O cliente recebe o token no login e o envia no header `Authorization: Bearer <token>` em todas as requisições seguintes.
