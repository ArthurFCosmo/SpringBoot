## 💠 O problema de armazenar senhas

Nunca armazene senhas em texto puro no banco de dados. Se o banco for comprometido — um vazamento, um backup mal protegido, um SQL Injection — todas as senhas de todos os usuários ficam expostas.

A evolução histórica do problema:

```
Texto puro    → "senha123"           ← qualquer um que ver o banco lê a senha
MD5/SHA-1     → "5f4dcc3b5aa765d..."  ← quebrável com Rainbow Tables
BCrypt        → "$2a$10$xK9..."       ← seguro: lento por design, com salt automático
```

O **BCrypt** é o algoritmo padrão do Spring Security para hash de senhas — e é o que usaremos na SGP.

---

## 💠 O que o BCrypt faz diferente

O BCrypt resolve os dois problemas dos algoritmos anteriores:

**1. Salt automático**
Cada vez que você hasheia uma senha com BCrypt, ele gera um valor aleatório chamado **salt** e o incorpora no resultado. Isso significa que a mesma senha "1234" gera hashes completamente diferentes a cada vez:

```
BCrypt("1234") → "$2a$10$xK9mN3pQrLvWzYjHbDcEuO..."
BCrypt("1234") → "$2a$10$7tRsKpNvMqXwYhFcGaDiUe..."
BCrypt("1234") → "$2a$10$3vLmJnHkPoBtRyEwCxFsAa..."
```

Três execuções, três resultados diferentes — mas todos verificáveis contra a senha original. Isso derrota as Rainbow Tables completamente.

**2. Lentidão intencional (fator de custo)**
O `10` no hash (`$2a$10$...`) é o **fator de custo**. Ele define quantas iterações o algoritmo executa. Fator 10 significa 2¹⁰ = 1.024 iterações. Isso faz o hash levar alguns milissegundos — imperceptível para um login normal, mas catastrófico para um ataque de força bruta que precisa testar bilhões de combinações.

## 💠 Como o BCrypt está configurado na SGP

Na página 42.0 já registramos o `PasswordEncoder` como bean:

```Java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

O `BCryptPasswordEncoder()` sem parâmetros usa fator de custo 10 por padrão — adequado para a maioria dos cenários. Em produção com requisitos mais altos de segurança, pode-se usar fator 12 ou 14.

## 💠 Onde o BCrypt é usado na SGP

### No registro — hasheando a senha antes de salvar

```Java
// AuthService — método de registro
public void registrar(RegisterRequestDTO dto) {
    String senhaHasheada = passwordEncoder.encode(dto.senha());

    UsuarioSistema novoUsuario = new UsuarioSistema(
        null,
        dto.email(),
        senhaHasheada,   // ← nunca a senha original
        dto.role()
    );

    usuarioSistemaRepository.save(novoUsuario);
}
```

### No login — verificando a senha

```Java
// O Spring Security faz isso automaticamente via AuthenticationManager
// mas por baixo dos panos acontece:
passwordEncoder.matches("senha123", "$2a$10$xK9mN3pQrLvWzYjHbDcEuO...");
// → true se a senha bate com o hash, false se não bate
```

O método `.matches(senhaRaw, senhaHash)` do `PasswordEncoder` é o responsável pela verificação. Ele pega a senha que o usuário digitou, aplica o mesmo processo de hash com o salt que está embutido no hash armazenado, e compara os resultados.

---

## 💠 O que o banco vai guardar

Quando um usuário for cadastrado com a senha `"1234"`, o banco vai armazenar algo assim na coluna `senha`:

```
$2a$10$xK9mN3pQrLvWzYjHbDcEuOrTbVwNsKpMqZjHfGaDiUeLnCmPoBtRy
```

Nunca `"1234"`. Mesmo que alguém acesse o banco diretamente, não consegue reverter o hash para a senha original.

---

## 💠 O que NÃO fazer

```Java
// ❌ Salvar a senha em texto puro
usuario.setSenha(dto.senha());

// ❌ Usar MD5 ou SHA manualmente
usuario.setSenha(DigestUtils.md5Hex(dto.senha()));

// ✅ Sempre usar o PasswordEncoder injetado
usuario.setSenha(passwordEncoder.encode(dto.senha()));
```

O `PasswordEncoder` injetado pelo Spring garante que o mesmo algoritmo usado para hashear é o mesmo usado para verificar — consistência garantida.

## 💠 Hash vs Criptografia

**Criptografia** (tipo AES) é uma via de mão dupla: você criptografa com uma chave, e existe uma operação matemática inversa que, com a chave certa, volta ao texto original. Existe uma função `descriptografar()`.

**Hash** (tipo BCrypt, MD5, SHA) é uma via de mão única: você transforma o texto num valor, mas **não existe operação matemática que reverta isso**. Não é que a reversão seja difícil — é que ela **não existe**. Não tem chave escondida, não tem "só o BCrypt sabe descriptografar". Ninguém descriptografa, nem os criadores do algoritmo, nem o Spring, nem ninguém.

### Por que não dá pra reverter matematicamente

Pensa assim: pega um número gigante, tipo `847293`, e faz `847293 % 100 = 93`. Eu te falo que o resultado foi `93`. Você consegue me dizer com certeza absoluta qual era o número original? Não — pode ter sido `847293`, `123493`, `999993`... infinitos números geram o mesmo resto.

Hash funciona numa lógica parecida (bem mais sofisticada matematicamente, mas o princípio é esse): é uma função que **perde informação de propósito**. Ela pega uma entrada de tamanho variável e sempre produz uma saída de tamanho fixo, misturando os bits de um jeito que não tem "volta".

### Então como o login funciona, se não dá pra reverter?

Não reverte — **compara**. Quando você faz login:

Java

```Java
passwordEncoder.matches("senha123", hashArmazenadoNoBanco);
```

Por baixo dos panos, isso não descriptografa o hash. Isso pega a senha que você digitou (`"senha123"`), aplica o **mesmo processo de hash de novo** (usando o salt que está embutido no hash armazenado), e compara o resultado novo com o hash guardado. Se bateram, a senha está correta — porque só a senha original, submetida ao mesmo processo, produziria aquele hash específico.

### E sobre "enganar" o algoritmo

Não tem engano possível porque não tem porta escondida pra abrir. O único jeito de "quebrar" um hash é **força bruta**: tentar senhas até uma bater. É exatamente por isso que o fator de custo do BCrypt existe — cada tentativa é _proposital e artificialmente lenta_. Com SHA-1, um atacante testa bilhões de senhas por segundo. Com BCrypt fator 10, ele testa uma fração disso, porque cada hash individual já é caro de calcular.

### Resumo direto

|                        | Criptografia      | Hash (BCript)                          |
| ---------------------- | ----------------- | -------------------------------------- |
| Existe função inversa? | Sim (com a chave) | Não, nunca                             |
| Como "desfaz"?         | Descriptografando | Não desfaz — recalcula e compara       |
| Ponto fraco explorável | Roubar a chave    | Só força bruta (por isso o custo alto) |

Não é que o BCrypt seja bom em _esconder_ a senha — é que a senha original literalmente **não está presente** no hash de nenhuma forma recuperável. É informação destruída por design, só que de um jeito verificável.

---

> 💡 **Resumo:** BCrypt é o algoritmo padrão do Spring Security para hash de senhas. Ele usa salt automático (derrota Rainbow Tables) e é lento por design (dificulta força bruta). O `PasswordEncoder` é injetado via `@Bean` e usado em dois momentos: `.encode()` no registro e `.matches()` na verificação do login. Nunca armazene senha em texto puro.
