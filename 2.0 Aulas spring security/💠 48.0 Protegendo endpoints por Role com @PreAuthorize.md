## 💠 O que é autorização por Role

Autenticação responde "quem é você?". Autorização responde "o que você pode fazer?".

Na SGP, todos os usuários autenticados têm um token válido — mas nem todos podem fazer tudo. Um `COLABORADOR` pode listar projetos, mas não pode deletar. Só um `ADMIN` pode deletar. Isso é autorização por role.

O Spring Security oferece duas formas de aplicar isso: via `SecurityFilterChain` (configuração centralizada) ou via `@PreAuthorize` (anotação diretamente no método). Usaremos `@PreAuthorize` — é mais explícito, fica junto ao código que protege, e é o padrão preferido no mercado.

---

## 💠 Como o `@PreAuthorize` funciona

O `@PreAuthorize` avalia uma expressão **antes** de executar o método. Se a expressão retornar `false`, o Spring lança `AccessDeniedException` — que o `GlobalExceptionHandler` vai capturar e devolver `403 Forbidden`.

A anotação foi habilitada na `SecurityConfig` com `@EnableMethodSecurity` — sem ela, `@PreAuthorize` seria ignorado silenciosamente.

---

## 💠 As expressões mais usadas

```Java
@PreAuthorize("hasRole('ADMIN')")
// ← só ADMIN passa

@PreAuthorize("hasAnyRole('ADMIN', 'GERENTE')")
// ← ADMIN ou GERENTE passam

@PreAuthorize("hasAnyRole('ADMIN', 'GERENTE', 'COLABORADOR')")
// ← qualquer autenticado passa (equivalente a só exigir autenticação)

@PreAuthorize("isAuthenticated()")
// ← qualquer usuário com token válido passa
```

O Spring verifica automaticamente o prefixo `ROLE_` — você escreve `'ADMIN'` e ele compara com `ROLE_ADMIN` nas authorities.

---

## 💠 Aplicando nas regras da SGP

Na SGP definimos as seguintes permissões:

| Operação | Roles permitidas |
|---|---|
| Listar / buscar qualquer coisa | `ADMIN`, `GERENTE`, `COLABORADOR` |
| Criar ou atualizar `Usuario`, `Projeto`, `Tarefa` | `ADMIN`, `GERENTE` |
| Deletar qualquer coisa | `ADMIN` |

## 💠 O UsuarioController protegido

```Java
@RestController
@RequestMapping("/usuario")
@RequiredArgsConstructor
@Tag(name = "Usuário")
public class UsuarioController {

    private final UsuarioService usuarioService;

    @PostMapping
    @PreAuthorize("hasAnyRole('ADMIN', 'GERENTE')")
    public ResponseEntity<UsuarioResponseDTO> salvarUsuario(
            @RequestBody @Valid UsuarioRequestDTO usuario) {
        return ResponseEntity.status(HttpStatus.CREATED)
            .body(usuarioService.salvarUsuario(usuario));
    }

    @GetMapping
    @PreAuthorize("hasAnyRole('ADMIN', 'GERENTE', 'COLABORADOR')")
    public ResponseEntity<List<UsuarioResponseDTO>> listarUsuarios() {
        return ResponseEntity.ok(usuarioService.listarUsuarios());
    }

    @GetMapping("/{id}")
    @PreAuthorize("hasAnyRole('ADMIN', 'GERENTE', 'COLABORADOR')")
    public ResponseEntity<UsuarioResponseDTO> buscarUsuarioPorId(@PathVariable Long id) {
        return ResponseEntity.ok(usuarioService.buscarUsuarioPorId(id));
    }

    @PutMapping("/{id}")
    @PreAuthorize("hasAnyRole('ADMIN', 'GERENTE')")
    public ResponseEntity<UsuarioResponseDTO> atualizarUsuario(
            @PathVariable Long id, @RequestBody @Valid UsuarioRequestDTO usuario) {
        return ResponseEntity.ok(usuarioService.atualizarUsuario(id, usuario));
    }

    @DeleteMapping("/{id}")
    @PreAuthorize("hasRole('ADMIN')")
    public ResponseEntity<Void> deletarUsuarioPorId(@PathVariable Long id) {
        usuarioService.deletarUsuarioPorId(id);
        return ResponseEntity.noContent().build();
    }
}
```

## 💠 O mesmo padrão para Projeto e Tarefa

O `ProjetoController` e o `TarefaController` seguem exatamente o mesmo padrão:

```Java
// Leitura — todos os roles
@GetMapping
@PreAuthorize("hasAnyRole('ADMIN', 'GERENTE', 'COLABORADOR')")
public ResponseEntity<List<ProjetoResponseDTO>> listarProjetos() { ... }

// Criação e atualização — ADMIN e GERENTE
@PostMapping
@PreAuthorize("hasAnyRole('ADMIN', 'GERENTE')")
public ResponseEntity<ProjetoResponseDTO> salvarProjeto(...) { ... }

// Deleção — só ADMIN
@DeleteMapping("/{id}")
@PreAuthorize("hasRole('ADMIN')")
public ResponseEntity<Void> deletarProjetoPorId(...) { ... }
```

## 💠 Adicionando o handler de `AccessDeniedException` no GlobalExceptionHandler

Quando um usuário autenticado tenta acessar um endpoint além do seu role, o Spring lança `AccessDeniedException`. Adicione o handler:

```Java
@ExceptionHandler(AccessDeniedException.class)
public ResponseEntity<ErroPadraoResponseDTO> tratarAccessDeniedException(
        HttpServletRequest request, AccessDeniedException exception) {
    return criarExeptionPadrao(
        request,
        HttpStatus.FORBIDDEN,
        "Acesso negado. Você não tem permissão para realizar esta operação."
    );
}
```

Agora um `COLABORADOR` tentando deletar um projeto recebe:

```JSON
{
    "timestamp": "2026-08-01T10:45:00",
    "status": 403,
    "error": "Forbidden",
    "message": "Acesso negado. Você não tem permissão para realizar esta operação.",
    "path": "http://localhost:8080/projeto/1"
}
```

## 💠 A diferença entre 401 e 403

| Status | Quando ocorre |
|---|---|
| `401 Unauthorized` | Sem token ou token inválido — o sistema não sabe quem é você |
| `403 Forbidden` | Token válido, mas seu role não tem permissão — o sistema sabe quem você é, mas não deixa passar |

A analogia: `401` é ser barrado na portaria por não ter crachá. `403` é ter crachá válido mas tentar entrar em um andar que seu crachá não libera.

---

> 💡 **Resumo:** `@PreAuthorize` protege métodos individuais com expressões de role. Requer `@EnableMethodSecurity` na `SecurityConfig`. `hasRole('ADMIN')` exige um role específico, `hasAnyRole(...)` aceita múltiplos. `AccessDeniedException` é lançada quando o role não tem permissão e deve ser tratada no `GlobalExceptionHandler` com `403 Forbidden`. A diferença entre `401` e `403` é autenticação vs autorização.
