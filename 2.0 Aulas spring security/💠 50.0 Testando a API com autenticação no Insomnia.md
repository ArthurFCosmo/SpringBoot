## 💠 O que mudou no Insomnia

Nas versões anteriores, qualquer requisição funcionava sem credenciais. Agora toda requisição protegida precisa de um token JWT no header `Authorization`. O fluxo de teste muda:

```
1. Registrar um usuário → POST /auth/register
2. Fazer login → POST /auth/login → copiar o token
3. Configurar o token no Insomnia
4. Testar os endpoints normalmente
```

---

## 💠 Passo 1 — Registrar um usuário ADMIN

```
POST localhost:8080/auth/register
```

```JSON
{
    "email": "arthurcosmo@gmail.com",
    "senha": "1234",
    "role": "ADMIN"
}
```

Resposta `201 Created`:
```JSON
{
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "email": "arthurcosmo@gmail.com",
    "role": "ADMIN"
}
```

Registre também outros usuários para testar as restrições de role:

```JSON
{ "email": "gerente@gmail.com", "senha": "1234", "role": "GERENTE" }
{ "email": "colaborador@gmail.com", "senha": "1234", "role": "COLABORADOR" }
```

---

## 💠 Passo 2 — Fazer login e obter o token

```
POST localhost:8080/auth/login
```

```JSON
{
    "email": "arthurcosmo@gmail.com",
    "senha": "1234"
}
```

Resposta `200 OK`:
```JSON
{
    "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "email": "arthurcosmo@gmail.com",
    "role": "ADMIN"
}
```

Copie o valor do campo `token`.

---

## 💠 Passo 3 — Configurar o token no Insomnia

**Opção A — Por requisição (mais simples):**
Em cada requisição protegida, vá na aba **Auth → Bearer Token** e cole o token no campo **Token**.

**Opção B — Variável de ambiente (recomendado):**
No Insomnia, crie uma variável de ambiente chamada `token` e cole o valor lá. Nas requisições, use `Bearer {{ _.token }}` no header `Authorization`. Assim você só precisa atualizar o token em um lugar quando ele expirar.

## 💠 Testando as restrições de autenticação

**Sem token — deve retornar 401:**
```
GET localhost:8080/projeto
(sem header Authorization)

→ 401 Unauthorized
{
    "message": "Credenciais inválidas. Verifique o e-mail e a senha."
}
```

**Com token inválido — deve retornar 401:**
```
GET localhost:8080/projeto
Authorization: Bearer tokeninvalido123

→ 401 Unauthorized
```

**Com token válido — deve retornar 200:**
```
GET localhost:8080/projeto
Authorization: Bearer eyJhbGci...

→ 200 OK (lista de projetos)
```

---

## 💠 Testando as restrições de role

**COLABORADOR tentando criar projeto — deve retornar 403:**

Faça login com `colaborador@gmail.com` e use o token dele:

```
POST localhost:8080/projeto
Authorization: Bearer <token do colaborador>
{ "nome": "Novo Projeto", ... }

→ 403 Forbidden
{
    "message": "Acesso negado. Você não tem permissão para realizar esta operação."
}
```

**COLABORADOR listando projetos — deve funcionar:**
```
GET localhost:8080/projeto
Authorization: Bearer <token do colaborador>

→ 200 OK
```

**GERENTE criando projeto — deve funcionar:**
```
POST localhost:8080/projeto
Authorization: Bearer <token do gerente>
{ ... }

→ 201 Created
```

**GERENTE tentando deletar projeto — deve retornar 403:**
```
DELETE localhost:8080/projeto/1
Authorization: Bearer <token do gerente>

→ 403 Forbidden
```

**ADMIN deletando projeto — deve funcionar:**
```
DELETE localhost:8080/projeto/1
Authorization: Bearer <token do admin>

→ 204 No Content
```

## 💠 Testando a máquina de estados

Com token de ADMIN ou GERENTE, teste as transições de status:

**Transição válida — ATIVO para CONCLUIDO:**
```
PUT localhost:8080/projeto/1
Authorization: Bearer <token>
{
    "nome": "SGP API",
    "status": "CONCLUIDO",
    "usuarioResponsavelId": 1,
    ...
}

→ 200 OK (projeto com status CONCLUIDO)
```

**Transição inválida — CONCLUIDO para CANCELADO:**
```
PUT localhost:8080/projeto/1
Authorization: Bearer <token>
{ "status": "CANCELADO", ... }

→ 422 Unprocessable Entity
{
    "message": "Transição de status inválida: não é possível ir de CONCLUIDO para CANCELADO."
}
```

## 💠 Tabela de endpoints completa com autenticação

### Auth (público)
| Método | URL | Role | O que faz |
|---|---|---|---|
| `POST` | `/auth/register` | Público | Registra usuário do sistema |
| `POST` | `/auth/login` | Público | Autentica e retorna token |

### Usuários
| Método | URL | Role mínimo | O que faz |
|---|---|---|---|
| `POST` | `/usuario` | `GERENTE` | Cadastra usuário |
| `GET` | `/usuario` | `COLABORADOR` | Lista todos |
| `GET` | `/usuario/{id}` | `COLABORADOR` | Busca por ID |
| `PUT` | `/usuario/{id}` | `GERENTE` | Atualiza |
| `DELETE` | `/usuario/{id}` | `ADMIN` | Deleta |

### Projetos
| Método | URL | Role mínimo | O que faz |
|---|---|---|---|
| `POST` | `/projeto` | `GERENTE` | Cadastra projeto |
| `GET` | `/projeto` | `COLABORADOR` | Lista todos |
| `GET` | `/projeto/{id}` | `COLABORADOR` | Busca por ID |
| `PUT` | `/projeto/{id}` | `GERENTE` | Atualiza / muda status |
| `DELETE` | `/projeto/{id}` | `ADMIN` | Deleta |
| `GET` | `/projeto/responsavel/{id}` | `COLABORADOR` | Projetos de um responsável |

### Tarefas
| Método | URL | Role mínimo | O que faz |
|---|---|---|---|
| `POST` | `/tarefa` | `GERENTE` | Cadastra tarefa |
| `GET` | `/tarefa` | `COLABORADOR` | Lista todas |
| `GET` | `/tarefa/{id}` | `COLABORADOR` | Busca por ID |
| `PUT` | `/tarefa/{id}` | `GERENTE` | Atualiza / muda status |
| `DELETE` | `/tarefa/{id}` | `ADMIN` | Deleta |

---

> 💡 **Resumo:** o fluxo de teste com autenticação é sempre — registrar, fazer login, copiar o token, configurar no Insomnia. Teste sempre os três cenários: sem token (401), token com role insuficiente (403), e token com role correto (200/201/204). Use variável de ambiente no Insomnia para não precisar colar o token em cada requisição manualmente.
