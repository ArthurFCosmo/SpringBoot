## 💠 O JwtService

Toda a lógica de geração e validação de tokens fica em uma única classe — o `JwtService`. Ele é responsável por três coisas:

- **Gerar** um token a partir de um `UsuarioSistema`
- **Extrair** o email (subject) de um token
- **Validar** se um token é legítimo e não expirou

Crie no pacote `service`:

```Java
@Service
public class JwtService {

    @Value("${api.security.token.secret}")
    private String secret;

    @Value("${api.security.token.expiration}")
    private Long expiration;

    public String gerarToken(UsuarioSistema usuario) {
        return Jwts.builder()
            .subject(usuario.getEmail())
            .claim("role", usuario.getRole().name())
            .issuedAt(new Date())
            .expiration(new Date(System.currentTimeMillis() + expiration))
            .signWith(getSigningKey())
            .compact();
    }

    public String extrairEmail(String token) {
        return extrairClaims(token).getSubject();
    }

    public boolean tokenValido(String token, UserDetails userDetails) {
        String email = extrairEmail(token);
        return email.equals(userDetails.getUsername()) && !tokenExpirado(token);
    }

    private boolean tokenExpirado(String token) {
        return extrairClaims(token).getExpiration().before(new Date());
    }

    private Claims extrairClaims(String token) {
        return Jwts.parser()
            .verifyWith(getSigningKey())
            .build()
            .parseSignedClaims(token)
            .getPayload();
    }

    private SecretKey getSigningKey() {
        byte[] keyBytes = Decoders.BASE64.decode(
            Base64.getEncoder().encodeToString(secret.getBytes())
        );
        return Keys.hmacShaKeyFor(keyBytes);
    }
}
```

---

## 💠 A anotação `@Value`

```Java
@Value("${api.security.token.secret}")
private String secret;

@Value("${api.security.token.expiration}")
private Long expiration;
```

O `@Value` injeta valores diretamente do `application.properties` em campos da classe. A sintaxe `${chave}` referencia a propriedade pelo nome exato que você definiu. Assim, a chave secreta e o tempo de expiração nunca ficam hardcoded no código.

---

## 💠 Gerando o token — `gerarToken()`

```Java
public String gerarToken(UsuarioSistema usuario) {
    return Jwts.builder()
        .subject(usuario.getEmail())         // ← quem é o usuário (sub)
        .claim("role", usuario.getRole().name()) // ← role no payload
        .issuedAt(new Date())                // ← quando foi gerado (iat)
        .expiration(new Date(System.currentTimeMillis() + expiration)) // ← quando expira (exp)
        .signWith(getSigningKey())           // ← assina com a chave secreta
        .compact();                          // ← serializa para String
}
```

O `Jwts.builder()` monta o token peça por peça:

| Método | Claim gerado | Descrição |
|---|---|---|
| `.subject()` | `sub` | Email do usuário — identificador principal |
| `.claim()` | `role` | Campo customizado — o role do usuário |
| `.issuedAt()` | `iat` | Timestamp de geração |
| `.expiration()` | `exp` | Timestamp de expiração |
| `.signWith()` | (assinatura) | Assina com HMAC-SHA256 |
| `.compact()` | — | Serializa o token para a String final |

---

## 💠 Extraindo informações — `extrairClaims()`

```Java
private Claims extrairClaims(String token) {
    return Jwts.parser()
        .verifyWith(getSigningKey())   // ← usa a mesma chave para verificar a assinatura
        .build()
        .parseSignedClaims(token)      // ← lê e valida o token
        .getPayload();                 // ← retorna o payload (Claims)
}
```

O `Jwts.parser()` faz o caminho inverso — recebe a String do token, verifica a assinatura com a chave secreta, e retorna um objeto `Claims` com todos os dados do payload. Se a assinatura não bater ou o token estiver malformado, ele lança uma exceção automaticamente.

---

## 💠 Validando o token — `tokenValido()`

```Java
public boolean tokenValido(String token, UserDetails userDetails) {
    String email = extrairEmail(token);
    return email.equals(userDetails.getUsername()) && !tokenExpirado(token);
}
```

A validação verifica duas coisas:

1. **O email do token bate com o usuário carregado do banco** — garante que o token pertence a quem diz pertencer
2. **O token não expirou** — verifica se a data de expiração ainda está no futuro

As duas condições precisam ser verdadeiras para o token ser considerado válido.

---

## 💠 A chave de assinatura — `getSigningKey()`

```Java
private SecretKey getSigningKey() {
    byte[] keyBytes = Decoders.BASE64.decode(
        Base64.getEncoder().encodeToString(secret.getBytes())
    );
    return Keys.hmacShaKeyFor(keyBytes);
}
```

O JJWT exige que a chave seja um objeto `SecretKey`, não uma String simples. Esse método converte a String do `application.properties` para o formato que o JJWT entende:

1. Pega a String `secret` e converte para bytes
2. Codifica em Base64
3. Decodifica de volta para bytes no formato que o JJWT espera
4. Gera a `SecretKey` com o algoritmo HMAC-SHA256

A mesma chave é usada na geração (`.signWith()`) e na validação (`.verifyWith()`). Se a chave for diferente em qualquer dos dois lados, a validação falha — o que impede tokens forjados por terceiros.

---

## 💠 O que acontece se o token for inválido

Se o token estiver malformado, com assinatura incorreta ou expirado, o `Jwts.parser()` lança exceções do JJWT que o filtro JWT (página 46.0) vai capturar e tratar — devolvendo `401 Unauthorized` para o cliente.

---

> 💡 **Resumo:** o `JwtService` centraliza toda a lógica de JWT. `gerarToken()` monta e assina o token com email, role e expiração. `extrairClaims()` lê e verifica o token. `tokenValido()` checa se o email bate e se não expirou. A chave secreta vem do `application.properties` via `@Value` e é convertida para `SecretKey` pelo JJWT.
