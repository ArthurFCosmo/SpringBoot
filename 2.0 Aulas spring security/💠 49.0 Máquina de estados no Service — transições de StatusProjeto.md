## 💠 O que é uma máquina de estados

Um projeto na SGP não pode ir de qualquer status para qualquer outro. Um projeto `CANCELADO` não pode voltar para `ATIVO`. Um projeto `CONCLUIDO` não pode ir direto para `CANCELADO` sem passar por `ATIVO`.

Esse conjunto de regras que controla quais transições são válidas chama-se **máquina de estados** — e é uma regra de negócio que vive no Service.

O fluxo definido para o `StatusProjeto` da SGP:

```
ATIVO ──────────────► CONCLUIDO
  │
  └───────────────► CANCELADO
```

Ou seja:
- `ATIVO` pode ir para `CONCLUIDO` ou `CANCELADO`
- `CONCLUIDO` não pode ir para lugar nenhum
- `CANCELADO` não pode ir para lugar nenhum

Transições inválidas devem ser rejeitadas com `422 Unprocessable Entity`.

## 💠 O enum StatusProjeto com as transições permitidas

A forma mais elegante de implementar isso é colocar a lógica de transição dentro do próprio enum:

```Java
public enum StatusProjeto {

    ATIVO {
        @Override
        public Set<StatusProjeto> transicoesPermitidas() {
            return Set.of(CONCLUIDO, CANCELADO);
        }
    },
    CONCLUIDO {
        @Override
        public Set<StatusProjeto> transicoesPermitidas() {
            return Set.of();
        }
    },
    CANCELADO {
        @Override
        public Set<StatusProjeto> transicoesPermitidas() {
            return Set.of();
        }
    };

    public abstract Set<StatusProjeto> transicoesPermitidas();

    public boolean podeTransicionarPara(StatusProjeto novoStatus) {
        return transicoesPermitidas().contains(novoStatus);
    }
}
```

Cada valor do enum sobrescreve `transicoesPermitidas()` com os status para os quais pode ir. O método `podeTransicionarPara()` é o que o service vai chamar para validar.

## 💠 Aplicando a validação no ProjetoService

O método `atualizarProjeto` precisa verificar a transição antes de salvar:

```Java
public ProjetoResponseDTO atualizarProjeto(Long id, ProjetoRequestDTO dto) {

    Projeto projetoExistente = projetoRepository.findById(id).orElseThrow(
        () -> new ElementoNaoEncontradoException("Não foi encontrado Projeto com o Id solicitado.")
    );

    StatusProjeto statusAtual = projetoExistente.getStatus();
    StatusProjeto novoStatus = converterParaEnumStatus(dto.status());

    if (!statusAtual.equals(novoStatus) && !statusAtual.podeTransicionarPara(novoStatus)) {
        throw new RegraDeNegocioVioladaException(
            "Transição de status inválida: não é possível ir de "
            + statusAtual + " para " + novoStatus + "."
        );
    }

    usuarioRepository.findById(dto.usuarioResponsavelId()).orElseThrow(
        () -> new ElementoNaoEncontradoException("Não foi encontrado Usuario com o ResponsavelId solicitado.")
    );

    return converterModelParaResponseDTO(
        projetoRepository.save(converterRequestDTOparaModel(id, dto))
    );
}
```

A condição de validação:

```Java
if (!statusAtual.equals(novoStatus) && !statusAtual.podeTransicionarPara(novoStatus))
```

- `!statusAtual.equals(novoStatus)` — se o status não mudou, não há transição para validar. Atualizar outros campos do projeto mantendo o mesmo status é sempre permitido.
- `!statusAtual.podeTransicionarPara(novoStatus)` — se mudou, verifica se a transição é permitida.

## 💠 Exemplos de transições e o que acontece

**Válida — ATIVO para CONCLUIDO:**
```JSON
PUT /projeto/1
{ "status": "CONCLUIDO", ... }
→ 200 OK
```

**Válida — ATIVO para CANCELADO:**
```JSON
PUT /projeto/1
{ "status": "CANCELADO", ... }
→ 422 Unprocessable Entity
```

**Inválida — CONCLUIDO para CANCELADO:**
```JSON
PUT /projeto/1
{ "status": "CANCELADO", ... }
→ 422 Unprocessable Entity
{
    "message": "Transição de status inválida: não é possível ir de CONCLUIDO para CANCELADO."
}
```

**Inválida — CANCELADO para ATIVO:**
```JSON
PUT /projeto/1
{ "status": "ATIVO", ... }
→ 422 Unprocessable Entity
{
    "message": "Transição de status inválida: não é possível ir de CANCELADO para ATIVO."
}
```

## 💠 Por que a lógica fica no enum e não no service

Você poderia colocar os `if/else` de transição diretamente no `ProjetoService`:

```Java
// Funciona, mas escala mal
if (statusAtual == StatusProjeto.CONCLUIDO || statusAtual == StatusProjeto.CANCELADO) {
    throw new RegraDeNegocioVioladaException("...");
}
```

O problema é que se o fluxo de estados crescer — novos status, novas regras — você vai precisar alterar o service. Colocando a lógica no enum, cada valor sabe suas próprias transições. Para adicionar um novo status `EM_REVISAO`, basta adicionar o valor no enum e definir suas transições — o service não precisa mudar.

É o princípio **Open/Closed**: aberto para extensão, fechado para modificação.

## 💠 O mesmo padrão para StatusTarefa

Se quiser aplicar o mesmo para `StatusTarefa`, o fluxo seria:

```
PENDENTE ──────────────► FAZENDO ──────────────► CONCLUIDA
                            │
                            └───────────────► PENDENTE
```

A implementação segue o mesmo padrão do `StatusProjeto` — cada valor do enum define suas transições permitidas.

---

> 💡 **Resumo:** máquina de estados controla quais transições de status são válidas. A lógica fica no próprio enum — cada valor define para onde pode ir via `transicoesPermitidas()`. O service chama `podeTransicionarPara()` antes de salvar e lança `RegraDeNegocioVioladaException` se a transição for inválida. Colocar a lógica no enum segue o princípio Open/Closed — novos estados não exigem alterar o service.
