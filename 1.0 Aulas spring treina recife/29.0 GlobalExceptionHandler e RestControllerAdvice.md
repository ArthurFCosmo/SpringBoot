## 💠 O problema sem o GlobalExceptionHandler

Quando uma exceção é lançada e ninguém a trata, o Spring devolve um `500 Internal Server Error` com a stacktrace completa — ilegível para o cliente e perigoso em produção (expõe detalhes internos).

Poderíamos colocar `try/catch` em cada controller, mas isso seria código repetido em todo lugar. A solução correta é centralizar o tratamento em um único lugar.

---

## 💠 A classe GlobalExceptionHandler

```Java
@RestControllerAdvice
public class GlobalExceptionHandler {
    // handlers aqui
}
```

A anotação `@RestControllerAdvice` faz o Spring registrar essa classe como um interceptador global de exceções. Toda vez que qualquer controller lançar uma exceção (ou receber uma do service), ela passa por aqui antes de chegar ao cliente.

É como um segurança na porta de saída da API — tudo que vai sair passa pela triagem dele.

---

## 💠 Os três handlers

Cada método trata um tipo de exceção e define o status HTTP de retorno:

```Java
// 404 — elemento não encontrado no banco
@ExceptionHandler(ElementoNaoEncontradoException.class)
public ResponseEntity<ErroPadraoResponseDto> tratarElementoNaoEncontradoException(
    HttpServletRequest request, ElementoNaoEncontradoException exception) {

    ErroPadraoResponseDto dto = new ErroPadraoResponseDto(
        LocalDateTime.now(), 404, "Elemento não encontrado.",
        exception.getMessage(), request.getRequestURL().toString()
    );
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(dto);
}

// 422 — regra de negócio violada
@ExceptionHandler(RegraDeNegocioVioladaException.class)
public ResponseEntity<ErroPadraoResponseDto> tratarRegraDeNegocioVioladaException(...) { ... }

// 400 — dados inválidos no body da requisição (@Valid falhou)
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErroPadraoResponseDto> tratarMethodArgumentNotValidException(...) { ... }
```

---

## 💠 Entendendo os parâmetros do handler

```Java
public ResponseEntity<ErroPadraoResponseDto> tratarElementoNaoEncontradoException(
    HttpServletRequest request,           // ← acesso à requisição que gerou o erro
    ElementoNaoEncontradoException exception  // ← a exceção capturada
)
```

- `HttpServletRequest request` — permite acessar a URL da requisição com `request.getRequestURL().toString()`. Isso entra no DTO de erro para o cliente saber qual endpoint gerou o problema.
- `exception` — o objeto da exceção, que carrega a mensagem que você escreveu no `throw`.

---

## 💠 A semântica dos status codes

| Status | Quando usar |
|---|---|
| `400 Bad Request` | O dado enviado está malformado ou inválido — `@Valid` falhou |
| `404 Not Found` | O recurso solicitado não existe no banco |
| `422 Unprocessable Content` | O dado é válido, mas viola uma regra de negócio |

A diferença entre `400` e `422` é sutil mas importante: `400` significa "não entendi o que você mandou". `422` significa "entendi perfeitamente, mas não posso processar porque viola uma regra". Tentar deletar um usuário com projetos vinculados é `422` — os dados são válidos, a regra que impede.

## 💠 O handler do `MethodArgumentNotValidException`

Esse handler é especial porque a exceção pode ter múltiplos erros de validação ao mesmo tempo (nome em branco E CPF inválido, por exemplo). Por isso usamos stream para formatar todos:

```Java
String mensagemFormatada = exception.getBindingResult().getFieldErrors()
    .stream()
    .map(e -> e.getField() + ": " + e.getDefaultMessage())
    .collect(Collectors.joining(", "));
```

Resultado: `"cpf: CPF inválido, nome: não deve estar em branco"`

Cada `FieldError` tem o nome do campo (`.getField()`) e a mensagem da anotação (`.getDefaultMessage()`). O `Collectors.joining(", ")` junta tudo numa string só.

---

> 💡 **Resumo:** `@RestControllerAdvice` registra a classe como interceptador global. Cada `@ExceptionHandler` define qual exceção capturar e o que devolver. O Controller fica completamente limpo — não executa nenhuma lógica de tratamento de erro.
