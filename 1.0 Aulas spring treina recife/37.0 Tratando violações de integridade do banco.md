
---

## 💠 O problema

Quando um cliente tenta cadastrar um usuário com um CPF ou e-mail que já existe no banco, o MySQL rejeita a operação por causa da constraint `unique` — e sem tratamento, isso chegava ao cliente como um `500 Internal Server Error` com uma stacktrace enorme.

O `500` é errado aqui por dois motivos: primeiro, o servidor não falhou — ele funcionou corretamente ao rejeitar o dado duplicado. Segundo, o cliente não consegue entender o que errou.

O status correto para esse caso é **`409 Conflict`** — significa "o recurso que você quer criar conflita com algo que já existe".

---

## 💠 A exceção que o Spring lança

Quando o banco rejeita uma inserção por violação de constraint (unique, not null, foreign key), o Spring encapsula esse erro numa `DataIntegrityViolationException`. Essa exceção já existia nas versões anteriores — só não estava sendo tratada.

---

## 💠 O handler no GlobalExceptionHandler

```Java
@ExceptionHandler(DataIntegrityViolationException.class)
public ResponseEntity<ErroPadraoResponseDTO> tratarViolacaoDeIntegridade(
    HttpServletRequest request,
    DataIntegrityViolationException exception) {

    return criarExeptionPadrao(
        request,
        HttpStatus.CONFLICT,
        "Já existe um registro com esses dados (CPF/E-mail)."
    );
}
```

Agora ao tentar cadastrar um CPF duplicado, o cliente recebe:

```JSON
{
    "timestamp": "2026-07-16T14:32:05.123",
    "status": 409,
    "error": "Conflict",
    "message": "Já existe um registro com esses dados (CPF/E-mail).",
    "path": "http://localhost:8080/usuario"
}
```

---

## 💠 Por que a mensagem é genérica?

Você pode ter notado que a mensagem não diz "CPF já cadastrado" ou "E-mail já cadastrado" — diz os dois juntos. O motivo é que o `DataIntegrityViolationException` é uma exceção genérica que pode ser lançada por qualquer violação de constraint no banco.

Para diferenciar CPF de e-mail, você precisaria inspecionar a mensagem interna da exceção — o que é frágil e depende do banco de dados. A abordagem correta para esse nível de detalhe seria validar **antes de salvar**, usando queries como `existsByCpf()` e `existsByEmail()` no repository. Isso é uma evolução futura.

---

> 💡 **Resumo:** `DataIntegrityViolationException` é lançada quando o banco rejeita uma inserção por dado duplicado. O handler no `GlobalExceptionHandler` a captura e devolve `409 Conflict` com uma mensagem clara, em vez do `500` genérico.
