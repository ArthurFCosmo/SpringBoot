## 💠 O problema das exceções genéricas

Na versão 2.0, quando algo dava errado — um id inexistente, por exemplo — o sistema retornava um `500 Internal Server Error` com uma stacktrace enorme e ilegível. Isso é ruim por dois motivos:

1. O cliente não consegue entender o que errou
2. O servidor está revelando detalhes internos da implementação (nomes de classes, linhas de código)

A solução é criar **exceções próprias**, com mensagens claras, e tratá-las de forma centralizada.

---

## 💠 Criando uma exceção customizada

Uma exceção customizada é simplesmente uma classe que herda de `RuntimeException`:

```Java
public class ElementoNaoEncontradoException extends RuntimeException {
    public ElementoNaoEncontradoException(String mensagem) {
        super(mensagem);
    }
}
```

Só isso. O `extends RuntimeException` faz ela se comportar como uma exceção normal do Java. O construtor recebe a mensagem que vai aparecer para o cliente e passa para o `super()` — que é o construtor da `RuntimeException`, que armazena a mensagem internamente.

Na v3.0 temos duas:

```Java
// Lançada quando um elemento não é encontrado no banco → HTTP 404
public class ElementoNaoEncontradoException extends RuntimeException { ... }

// Lançada quando uma regra de negócio é violada → HTTP 422
public class RegraDeNegocioVioladaException extends RuntimeException { ... }
```

---

## 💠 Por que `RuntimeException`?

Em Java existem dois tipos de exceção:
- **Checked exceptions** — o compilador te força a tratar com `try/catch` ou declarar no método com `throws`
- **RuntimeException** — não obriga tratamento explícito, o Spring consegue interceptar automaticamente

Herdando de `RuntimeException`, o Spring consegue capturar a exceção em qualquer ponto da aplicação e redirecioná-la para o `GlobalExceptionHandler` — sem precisar de `try/catch` em todo lugar.

---

## 💠 Onde lançar

As exceções são lançadas no **Service**, que é onde mora a lógica de negócio:

```Java
// ElementoNaoEncontradoException — elemento não existe no banco
public UsuarioResponseDTO buscarUsuarioPorId(Long id){
    Usuario usuario = usuarioRepository.findById(id).orElseThrow(
        () -> new ElementoNaoEncontradoException("Não foi encontrado Usuario com o Id solicitado.")
    );
    return converterModelParaResponseDTO(usuario);
}

// RegraDeNegocioVioladaException — regra de negócio impediu a operação
public void deletarUsuarioPorId(Long id){
    ...
    if (projetoRepository.existsByResponsavel_Id(id)) {
        throw new RegraDeNegocioVioladaException(
            "O usuário não pôde ser deletado pois existem projetos em que ele é o responsável."
        );
    }
    ...
}
```

---

> 💡 **Resumo:** exceções customizadas são classes simples que herdam de `RuntimeException`. Elas carregam uma mensagem descritiva e são lançadas no service quando algo dá errado. O tratamento centralizado acontece no `GlobalExceptionHandler`.
