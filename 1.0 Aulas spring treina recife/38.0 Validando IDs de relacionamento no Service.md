## 💠 O problema

Quando um cliente cria ou atualiza uma tarefa, ele manda um `projetoId` e um `usuarioResponsavelId` no body. Esses ids precisam existir no banco — mas nada impede o cliente de mandar um id que não existe.

Sem validação:

```
POST /tarefa
{ "projetoId": 999 }  ← projeto que não existe
```

O `converterRequestDTOparaModel` faria `findById(999).orElse(null)`, o projeto viraria `null`, e o banco rejeitaria com `500` porque o campo tem `nullable = false`.

---

## 💠 A solução: validar antes de converter

No `salvarTarefa` e no `atualizarTarefa`, validamos os ids antes de chegar na conversão:

```Java
public TarefaResponseDTO salvarTarefa(TarefaRequestDTO tarefa) {

    // 1. Valida se o projeto existe
    projetoRepository.findById(tarefa.projetoId()).orElseThrow(
        () -> new ElementoNaoEncontradoException("Não foi encontrado um Projeto com o ProjetoId solicitado.")
    );

    // 2. Valida o responsável — mas só se foi informado (campo opcional)
    if (Objects.nonNull(tarefa.usuarioResponsavelId())) {
        usuarioRepository.findById(tarefa.usuarioResponsavelId()).orElseThrow(
            () -> new ElementoNaoEncontradoException("Não foi encontrado um Usuário com o UsuarioResponsavelId solicitado.")
        );
    }

    // 3. Só então converte e salva
    return converterModelParaResponseDTO(tarefaRepository.save(converterRequestDTOparaModel(tarefa)));
}
```

---

## 💠 Por que o responsável é tratado diferente do projeto?

O `projetoId` é **obrigatório** — toda tarefa precisa de um projeto. Por isso a validação é direta, sem verificar null.

O `usuarioResponsavelId` é **opcional** — uma tarefa pode existir sem responsável atribuído. Por isso a validação só acontece `if (Objects.nonNull(...))`. Se o cliente não mandar o campo, não há nada para validar.

```Java
if (Objects.nonNull(tarefa.usuarioResponsavelId())) {
    // só valida se foi informado
}
```

`Objects.nonNull(x)` é equivalente a `!Objects.isNull(x)` — apenas mais legível. Prefira o `nonNull` quando a intenção é "se existir, valida".

---

## 💠 O que o `@Valid` não cobre

O `@Valid` no controller valida **formato** — campos em branco, nulos, tamanho, padrão. Ele não tem como saber se um `Long id` existe no banco.

Por isso a responsabilidade de validar ids de relacionamento é sempre do **Service** — que tem acesso aos repositories e pode consultar o banco.

```
@Valid (Controller)      → formato dos dados
Service (validação manual) → existência dos ids no banco
```

---

> 💡 **Resumo:** ids de relacionamento precisam ser validados manualmente no service antes de converter para model. O projeto usa `orElseThrow` para ids obrigatórios e `if (nonNull)` + `orElseThrow` para ids opcionais. O `@Valid` do controller não cobre esse tipo de validação.
