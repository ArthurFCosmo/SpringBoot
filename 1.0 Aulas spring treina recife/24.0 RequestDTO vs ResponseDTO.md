## 💠 O problema do DTO único

Na versão 2.0 da API, usávamos um único DTO para entrada e saída. Isso criava um problema silencioso: o cliente podia mandar um `id` no body da requisição de cadastro, e o sistema tentava usar esse `id` para criar o registro — podendo sobrescrever um registro existente ou gerar comportamentos imprevisíveis.

Além disso, o mesmo DTO que recebia dados precisava servir para exibir dados — e às vezes o que faz sentido exibir é diferente do que faz sentido receber.

---

## 💠 A solução: dois DTOs por entidade

Na versão 3.0, cada entidade passou a ter dois DTOs:

```
Cliente → API         API → Cliente
──────────────────    ──────────────────
UsuarioRequestDTO     UsuarioResponseDTO
ProjetoRequestDTO     ProjetoResponseDTO
TarefaRequestDTO      TarefaResponseDTO
```

- **RequestDTO** — define o que a API aceita. Não tem `id` (o banco gera). Tem validações. Recebe dados no formato bruto do cliente.
- **ResponseDTO** — define o que a API devolve. Tem `id`. Pode ter campos calculados (como `idade`), campos mascarados (como `cpfMascarado`), e dados formatados (como datas em `dd/MM/yyyy`).

---

## 💠 Por que isso importa

Pensa assim: um formulário de cadastro num site tem campos como nome, e-mail, senha. Mas a resposta que o sistema devolve nunca inclui a senha — ela vai para o banco, mas não volta pro cliente. Com um DTO único, você precisaria de gambiarras para omitir campos. Com dois DTOs separados, a diferença é estrutural — o `UsuarioResponseDTO` simplesmente não tem o campo `senha`.

O mesmo raciocínio vale para o `id`: o RequestDTO não tem `id` porque o cliente não deve definir o próprio id. O ResponseDTO tem porque o cliente precisa saber qual id foi gerado para fazer buscas futuras.

---

## 💠 Como ficou na prática

```Java
// RequestDTO — o que entra
public record UsuarioRequestDTO(
    String nome,
    String cpf,
    String email,
    String senha,
    LocalDate dataNascimento,
    String status
) {}

// ResponseDTO — o que sai
public record UsuarioResponseDTO(
    Long id,         // ← gerado pelo banco, não existe no Request
    String nome,
    String cpfMascarado,  // ← mascarado, não o CPF bruto
    String email,
    LocalDate dataNascimento,
    int idade,       // ← calculado, não existe no banco
    String status
) {}
```

A `senha` entrou, foi ao banco, mas nunca voltou. O `cpf` entrou bruto, mas voltou mascarado. A `idade` nem entrou — foi calculada na hora de montar a resposta.

---

> 💡 **Resumo:** RequestDTO = contrato de entrada (o que a API aceita). ResponseDTO = contrato de saída (o que a API devolve). São coisas diferentes e devem ser modeladas separadamente.
